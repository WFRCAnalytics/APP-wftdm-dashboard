# Phase 0 Research: ZoneMapPanel

## §1. Deck.gl vs. pure MapLibre — confirmed pure MapLibre, no capability gap found

Per spec.md's own explicit standard (Grammar findings #4, FR-004): existing project documentation already pointed to pure MapLibre, but planning was required to confirm no real, specific capability gap forces deck.gl before treating that as final — not to reopen the question from scratch, and not to rubber-stamp it either.

**What a choropleth actually needs, checked against MapLibre's real, current API**:
- **Data-driven fill color** — MapLibre's `fill-color` paint property natively accepts `['interpolate', ['linear'], ['get', <field>], ...]` (continuous) or `['step', ['get', <field>], ...]` (quantized/stepped) expressions, evaluated per-feature directly by the GPU-backed style engine. Covers both a continuous `color_scale: sequential`/`diverging` ramp and a `steps`-quantized one (§10) with no additional library.
- **Hover/click value inspection** (spec.md User Story 1, Scenario 4) — MapLibre's own `map.on('mousemove', layerId, handler)` / `map.on('mouseleave', layerId, handler)` / `map.on('click', layerId, handler)` deliver the hovered/clicked feature's full properties directly (the same `queryRenderedFeatures` mechanism under the hood) — no deck.gl picking layer needed.
- **`setData()` updates** — already `project-docs/SPEC.md`'s own documented mechanism; a plain MapLibre `GeoJSONSource`, no `MapboxOverlay` involved at all.

**Confirmed against a real, fetched reference implementation**, not asserted from the API alone: `ar-puuk/spatial-sql-explorer` — Principle VIII's own designated reference for "DuckDB spatial extension lazy-load, MapLibre choropleth, basemap switching" — ships a real "Graduated" choropleth mode (Quantile/Equal Interval/Natural Breaks classification, multiple color ramps) with its stated tech stack naming DuckDB spatial + MapLibre only; no deck.gl dependency anywhere in its own README or stack description. This is independent confirmation, from the project's own designated reference for exactly this feature, that a production-quality choropleth has already been built this way without deck.gl.

**Decision**: `ZoneMapPanel` renders via a plain `maplibregl.Map` + one `GeoJSONSource` + one `fill` layer with a data-driven `fill-color` paint expression. No `@deck.gl/*` import, no `MapboxOverlay`, no second WebGL context. This makes `zonemap` the first map-rendering panel type entirely outside `012-webgl-context-management`'s interleaved-mode/`setStyle()`-survival/context-loss-detection scope — none of that machinery applies here, by design, not by oversight (a plain MapLibre source/layer survives its own map's `setStyle()` calls via the same `transformStyle` preservation mechanism `011`/`012` already built for exactly this purpose — see §9).

**Alternatives considered**: A deck.gl `GeoJsonLayer`/`SolidPolygonLayer` (interleaved, per FR-004's own fallback instruction) was considered and rejected — no picking/interaction need MapLibre's native mouse events don't already cover, no rendering need (thousands of simple polygons) that would exceed MapLibre's own vector-tile-scale fill-layer performance. Revisit only if a future requirement needs something MapLibre's paint expressions genuinely cannot express (e.g. per-feature 3D extrusion tied to a second numeric field) — not anticipated by anything in spec.md.

## §2. DuckDB-WASM spatial extension — not bundled, real confirmed network fetch, extends the existing parquet-extension caveat

Confirmed directly against DuckDB-WASM's own current docs and a real, fetched reference implementation, not assumed from general DuckDB knowledge (per spec.md's own explicit instruction):

- **Not autoloaded.** DuckDB's own docs (`duckdb.org/docs/lts/clients/wasm/extensions`) list only `autocomplete`, `excel`, `fts`, `icu`, `inet`, `json`, `parquet`, `sqlite`, `sqlsmith`, `tpcds`, `tpch` as the extensions with special (bundled/autoload) handling in DuckDB-WASM — `spatial` is not among them. It must be loaded explicitly: `INSTALL spatial; LOAD spatial;` — `INSTALL` is a no-op in DuckDB-WASM (no durable cross-session storage), and the real fetch happens on `LOAD`, which "will fetch (and decompress on the fly), perform signature checks and dynamically load via the Emscripten implementation of `dlopen`."
- **Fetched from `extensions.duckdb.org`**, the same host/mechanism `project-docs/ARCHITECTURE.md`'s existing caveat already documents for `parquet` — URL shape `extensions.duckdb.org/duckdb-wasm/$version_hash/$platform/spatial.duckdb_extension.wasm`, pre-compressed with Brotli.
- **Independently confirmed by a real, fetched reference implementation**: `ar-puuk/spatial-sql-explorer`'s own README states outright, "Installation of the DuckDB spatial extension requires an internet connection on first load, as it downloads the extension WASM binary from the DuckDB CDN" — the project's own designated Principle VIII reference for this feature has already found and documented the exact same gap independently.

**Decision**: `project-docs/ARCHITECTURE.md`'s existing "no internet required" caveat (found during `010-flowmap-panel` for the `parquet` extension) is extended during this feature's implementation to name `spatial` as a second, now-confirmed exception — not left as a second silently-undocumented gap (FR-014). The extension is loaded once, lazily, the first time any `zonemap` panel needs it (mirroring `ar-puuk/parquet-viewer`'s own confirmed "loads lazily — only when a spatial file is detected" pattern) — not eagerly at app boot, so a dashboard with no `zonemap` panels never pays this cost. Self-hosting `spatial` via `custom_extension_repository` (the same fix already tracked, unimplemented, for `parquet` — see this session's own project memory) is a natural follow-up once both extensions need it, but is out of scope for this feature to implement, matching `010`'s own precedent of documenting rather than fixing the `parquet` case.

## §3. Loading `boundaries` geometry — `registerFileURL()` + `read_parquet()` + `ST_GeomFromWKB()`, never `ST_Read()`/`registerFileBuffer()`

**A real, confirmed upstream bug rules out one otherwise-plausible design.** `duckdb/duckdb-wasm` discussion/issue `#1791` (escalated to bug report `#1793`) confirms `ST_Read()` — the GDAL-based multi-format vector reader `project-docs/SPEC.md`'s own illustrative "ZoneMapPanel wiring" snippet uses (`ST_AsGeoJSON(geom) FROM taz_zones`, without showing how `taz_zones` itself is created) — fails against files registered via `registerFileHandle()`/`registerFileBuffer()` with `IO Error: Unknown file type`, while the identical read succeeds against a file registered via an HTTP(S) URL. `services/duckdb.ts`'s own `registerScenario()` (the local-folder-picker path) uses exactly `registerFileBuffer()` — the confirmed-broken path — for every scenario's tabular Parquet views today, which is fine for those (they use `read_parquet()`, not `ST_Read()`), but would be a real, confirmed failure if `boundaries` geometry were ever loaded the same way.

**This is avoided by design, not merely defensively**: zone geometry is scenario-independent (the same TAZ boundaries apply regardless of which model run is loaded) and is never part of any scenario's own `summary/` folder — so it was never going to go through `registerScenario()`'s buffer-registration path in the first place. `boundaries: taz.geoparquet` resolves to a URL under a new, dedicated published static-asset directory (`public/geometry/`, plan.md's Project Structure) and is registered via `services/duckdb.ts`'s existing `registerFileURL()` — the confirmed-working path — exactly like `public/scenarios/`/`public/observed/`'s own Parquet files and `public/dashboard-config/`'s own YAML files already are.

**Geometry parsing avoids `ST_Read()` entirely, using plain `read_parquet()` + spatial scalar functions instead** — confirmed as the correct, more broadly portable approach against `ar-puuk/parquet-viewer` (Principle VIII's own designated reference for "GeoParquet metadata detection... spatial extension fallback"), whose own real approach reads the `geo` key from GeoParquet's standard key-value metadata and supports WKB (BLOB), WKT (VARCHAR), and native DuckDB `GEOMETRY` columns directly via `read_parquet()` — not the GDAL translator layer `ST_Read()` goes through. Concretely:

```sql
INSTALL spatial; LOAD spatial;   -- once per session, lazily (§2)
SELECT
  "<boundaries_id column>" AS zone_id,
  ST_AsGeoJSON(ST_GeomFromWKB(geometry)) AS geojson
FROM read_parquet('<registered boundaries URL>')
```

(The exact geometry-column name and whether it's native `GEOMETRY` vs. WKB `BLOB` is confirmed against the fixture/real file at implementation time — `ST_GeomFromWKB` is a no-op-equivalent skip when the column is already a native `GEOMETRY` type, per DuckDB spatial's own documented function overloads.)

**Decision**: `zoneGeometry.ts` registers `boundaries` via `registerFileURL()` and queries it via `read_parquet()` + `ST_AsGeoJSON()`/`ST_GeomFromWKB()` — never `ST_Read()`, never `registerFileBuffer()`. `project-docs/GRAMMAR.md`'s own `boundaries: taz.geoparquet` key is documented (data-model.md) as resolving relative to `public/geometry/`, a new dedicated static-asset directory — not `public/dashboard-config/` (considered and rejected in Phase 1 design review — see plan.md's post-Phase-1 Constitution Check note — since geometry is tab/dashboard-independent, unlike `dashboard-*.yaml`).

## §4. Zone geometry cache eviction policy — accepted tradeoff, no eviction (FR-003a, stated explicitly per spec.md's own requirement)

Spec.md's FR-003a requires this decision to be recorded explicitly here, not left implicit, mirroring the `extensions.duckdb.org` gap that sat undocumented until `010` happened to surface it.

**Decision: accepted, deliberate tradeoff — no eviction.** The module-level geometry cache in `zoneGeometry.ts` (keyed by `boundaries` filename/URL) persists for the full page-session lifetime, regardless of how many panels referencing it have mounted or unmounted. No cap, no LRU.

**Reasoning**:
- A `boundaries` file represents a fixed geographic zone system (TAZ, district, etc.) for a region — a WFRC deployment realistically has one or two distinct `boundaries` files in active use at a time (e.g. a TAZ-level file and possibly a coarser district-level file), not an open-ended or user-generated set. This is a fixed, small, analyst-authored catalog (like `dashboard-*.yaml` itself), not per-user or per-request content.
- The real WFRC/UGRC TAZ dataset (`data.wfrc.org`'s "Traffic Analysis Zones (TAZ), Wasatch Front" — confirmed real and current via live search, §5) is in the low thousands of zones at typical simplification levels — a parsed GeoJSON `FeatureCollection` at that scale is a few MB at most, not the kind of payload that meaningfully strains a long-running browser tab's memory over a single analyst session.
- This tool is an internal calibration dashboard for a small analyst team (`project-docs/ARCHITECTURE.md`'s own stated deployment model — `wftdm-dashboard serve`/`here`, not a public multi-tenant service), not a scenario where hundreds of distinct large geometry files could accumulate in one session.
- Building real LRU eviction now would add real complexity (a size/recency policy, re-fetch-on-evict handling for a still-mounted panel) to guard against a growth pattern nothing in this project's actual usage model produces.

**Revisit trigger, stated explicitly rather than left open-ended**: if a future feature (e.g. a per-scenario or per-user custom `boundaries` upload) makes the set of distinct `boundaries` files genuinely open-ended or large, add a basic LRU cap at that point — not preemptively here.

## §5. GeoParquet zone-boundary fixture — synthetic, not the real WFRC/UGRC dataset

A real, small, public Utah/WFRC-area zone-boundary dataset was confirmed to exist: WFRC's own Open Data portal (`data.wfrc.org`) publishes "Traffic Analysis Zones (TAZ), Wasatch Front" and a statewide equivalent, downloadable as shapefile/file geodatabase/KML/CSV, and UGRC (`gis.utah.gov`) separately publishes related SGID planning/boundary datasets. This confirms a real production data source exists for authors publishing an actual `boundaries` file — cited here for that purpose.

**Decision: the automated test fixture is synthetic, not this real dataset.** Every fixture `tests/fixtures/generate.py` has ever produced (`001` through `012`) is "tiny synthetic... hard-codes a handful of rows... zero aggregation, join, or transform logic" (the file's own header comment) — a deliberate, consistent project convention, not an oversight. The real WFRC TAZ dataset is hundreds of zones with genuinely complex polygon boundaries — the wrong shape for a "tiny" fixture, and pulling a real external dataset into the fixture generator would introduce the one thing `generate.py` has never had: an external data dependency. `generate.py` gains a small, hand-authored set of ~6-8 simple synthetic polygons (e.g. a 2×3 or 2×4 grid of adjacent rectangles, easy to reason about and to hand-verify a join/color-scale computation against), written to GeoParquet via DuckDB spatial's own `ST_AsWKB()`/`COPY ... TO ... (FORMAT PARQUET)` — the same offline geometry-to-GeoParquet conversion `project-docs/SPEC.md`'s own post-processor pipeline already documents (`ST_Read`/GeoPandas → GeoParquet), applied here to a hand-authored geometry instead of a real converted shapefile.

**Alternatives considered**: downsampling/simplifying the real WFRC TAZ dataset to a handful of zones was considered and rejected — it would still be an external, licensed dataset checked into (or fetched by) a test-fixture generator that has deliberately never had one, for no real test benefit over an equally-effective hand-authored synthetic set.

## §6. Hover/click value-inspection mechanics

Resolved directly by §1's pure-MapLibre decision: `map.on('mousemove', 'zonemap-fill', handler)` reads the hovered feature's `properties` (zone id + joined metric value, already present on each GeoJSON feature from the `zoneGeometry.ts`/data-join step) and renders a `maplibregl.Popup` (or an equivalent lightweight overlay) showing them; `mouseleave` clears it. No deck.gl `onHover`/picking layer needed — this is MapLibre's own native interaction API, not a new mechanism this feature invents.

## §7. `comparison: diff`'s `expr` computation — SQL-side string substitution, never a client-side evaluator or `eval()`

Grammar findings #8 flagged this as genuinely new: no prior panel type computes a per-row expression referencing two *named* scenarios' own columns in one panel.

**Decision**: `expr` (e.g. `"b.vmt_per_capita - a.vmt_per_capita"`) is substituted as a literal SQL fragment into a generated query — never parsed or evaluated in JavaScript, and never passed through `eval()` (constitution Principle III is explicit and non-negotiable on this point). `panelQuery.ts` gains a small `buildComparisonDiffQuery()` helper, structurally the same "plain string templating" discipline `services/sqlExpander.ts` already uses for `$sql.x`/`$mappings.x`:

```sql
SELECT a."<metric_id>" AS zone_id, (<expr>) AS diff_value
FROM "<scenario a view>__<metric>" a
JOIN "<scenario b view>__<metric>" b ON a."<metric_id>" = b."<metric_id>"
```

`a`/`b` are fixed, code-generated table aliases (never author-controlled beyond *which scenario name* they bind to); `<expr>` itself is copied verbatim from the panel's own YAML config, exactly like every other `$sql.x` fragment already is — DuckDB's own SQL engine evaluates the arithmetic, matching how `summarize.yaml`'s own metric SQL already lets an author write arbitrary SQL expressions with no separate expression-language layer above it.

**Correction, found while implementing this query builder against the real `panelQuery.ts` (not assumed from this research note's own first draft)**: `a`/`b` are NOT validated against `resolveActiveScenarios()`'s "currently active" set before the query is built — checked directly against `resolveActiveScenarios()`'s real implementation and found it performs no validation at all (`return config.scenarios ?? globallyActive` — a plain fallback, nothing that throws or checks existence), and `buildPanelQuery()`'s own `config.scenario` (singular) path does the same: it interpolates `${config.scenario}__${config.metric}` directly into the SQL with zero upfront existence/activity check, relying entirely on DuckDB rejecting a query against a nonexistent view at query time — caught by the panel's already-existing `.catch()` → `PanelErrorState`. `buildComparisonDiffQuery()` follows that exact same, simpler, already-established convention: `a`/`b` are interpolated as literal view-name prefixes with no upfront validation of any kind (not "active," not "registered") — an unresolvable name (or a real-but-currently-inactive scenario, which is fully queryable regardless of its "active" UI state, since `services/scenarioDiscovery.ts` registers every discovered scenario's views at boot time, unconditionally) fails naturally via DuckDB's own "table does not exist" error, mapped to the shared error state the same way every other unresolvable panel configuration already is (FR-010). This is simpler than originally drafted, not more complex — no new validation logic is introduced at all.

**Alternatives considered**: a client-side arithmetic evaluator (parsing `expr` and evaluating it in JS against two fetched row sets) was considered and rejected — it would be a new, bespoke expression-parsing surface with no existing precedent anywhere in this codebase, more complex than the SQL-side approach, and would still need to guard against becoming a de facto `eval()` if not built with real care; the SQL-side approach reuses the exact string-substitution discipline the constitution already mandates and every other placeholder in this app already follows.

## §8. Named `color_ramp` resolution + token-derived fallback

Grammar findings #7 corrected the request's own pointer to `008-sankey-panel`'s `color_scheme` (a categorical named-palette convention, `sankeyColor.ts`) — the actual structural precedent for zonemap's *continuous* `sequential`/`diverging` + `domain` grammar is `005-table-panel`'s `tableLogic.ts` `cellColor()` (token-derived, `MAX_COLOR_STRENGTH = 40`-capped `color-mix()`, diverging midpoint anchored at literal zero). Zonemap's `color_ramp` (a named ramp — the grammar's own worked examples are `YlOrRd`/`RdBu`, both real ColorBrewer names) has no equivalent in either precedent alone.

**Decision**: a new `panels/zonemapColor.ts` combines both precedents' shapes rather than literally reusing either file:
- When `color_ramp` names a recognized value, resolve it via `d3-scale-chromatic`'s matching interpolator (`interpolateYlOrRd`, `interpolateRdBu` — both real exports, already a project dependency via `008`) evaluated across the value's normalized position in `domain` — mirroring `sankeyColor.ts`'s `resolveNamedColorScheme()`'s recognized-name-else-`undefined` shape (a small `NAMED_RAMPS` lookup, not every `d3-scale-chromatic` export).
- When `color_ramp` is omitted or unrecognized, fall back to `tableLogic.ts`'s existing two-token convention unchanged (`--brand-wfrc-blue` sequential / `--destructive`+`--brand-wfrc-blue` diverging, capped `color-mix()` blend, zero-anchored diverging midpoint, out-of-domain clamping) — the same fallback-is-the-token-default relationship `sankeyColor.ts` already establishes for `color_scheme`.
- `steps` (§10), when present, quantizes either path's output into that many discrete bands before assigning a feature's fill color, rather than a fully continuous interpolation.

**Alternatives considered**: inventing an entirely new named-ramp catalog independent of `d3-scale-chromatic` was rejected — the library is already a project dependency (via `008-sankey-panel`) and both grammar-documented names (`YlOrRd`, `RdBu`) are real, standard exports, so no new dependency or bespoke color-math is needed.

## §9. Surviving 004's DOM relocation and `setStyle()` basemap switches — extends `010`'s finding, one lightweight additional check

`010-flowmap-panel`'s own empirical finding (a real Playwright-verified same-document `appendChild` reparent of the map's container survives cleanly, WebGL context intact) already answers the base-canvas-survival question for `maplibregl.Map` generally — `zonemap`'s map instance is the same kind of object, so this is not re-derived from scratch here. What's new and specific to `zonemap` is a plain `GeoJSONSource`'s `setData()` lifecycle across that same relocation, and across a basemap `setStyle()` switch — resolved as follows:

- **004 relocation**: since the container element itself is never replaced (004 moves a persistent *ancestor* node, `010`'s own finding), the `map` instance, its sources, and its layers are the same objects before and after — `setData()` calls before/after relocation act on the same live source. One lightweight Playwright check (relocate, then call `setData()` again, confirm the choropleth still updates) confirms this rather than re-running `010`'s full original investigation.
- **Basemap `setStyle()` switches**: unlike `010-flowmap-panel`'s deck.gl overlay (which lives *outside* MapLibre's own style — `011`'s `transformStyle` mechanism was built to preserve exactly this kind of app-added, non-basemap layer across a style swap), `zonemap`'s fill layer is a genuine MapLibre-native style layer. `011`'s existing `transformStyle` callback (`FlowMapPanel.tsx`'s basemap-application effect, reused verbatim per constitution Principle VIII's own `APP-WFRC-Commute-Patterns` reference) already preserves any previous-style layer whose id isn't already present in the new style, explicitly excluding only `BLANK_STYLE`'s own scaffolding layers (`BLANK_STYLE_LAYER_IDS`) — `zonemap`'s own `zonemap-fill`/`zonemap-zones` source+layer ids are exactly the kind of "future app-added custom layer" that mechanism's own comment already anticipated (`FlowMapPanel.tsx`'s own inline comment: "e.g. a later zonemap's choropleth fill" — written during `011`/`012`, confirming this was expected). No new basemap-survival mechanism is needed — `zonemap` re-runs the same effect shape unmodified.

**Decision**: `ZoneMapPanel.tsx` reuses `011`'s existing basemap-application effect shape (via `resolveEffectiveBasemap`/`loadBasemapStyle`/`basemapKey`, FR-005) unmodified, relying on its already-built `transformStyle` layer-preservation for the choropleth's own source/layer to survive a basemap switch. One new Playwright test confirms this for real (a basemap switch, then confirming the choropleth fill is still present and correctly colored) rather than assuming the existing mechanism's own documented intent is sufficient without checking.

## §10. `steps` — discrete color-band quantization

`project-docs/GRAMMAR.md` documents `steps: 7` alongside `color_scale`/`color_ramp`/`domain` with no further explanation, and neither `tableLogic.ts` (continuous only, no quantization concept at all) nor `sankeyColor.ts` (categorical, not continuous) has an equivalent.

**Decision**: `steps`, when present, quantizes the resolved color scale (§8) into that many discrete color bands across `domain` before assigning a feature's fill — a `d3.scaleQuantize`-equivalent step applied on top of §8's continuous interpolation, not a replacement for it (a natural, standard choropleth convention — discrete class breaks are the norm for a printed/reference choropleth, continuous is more common for on-screen interactive ones; supporting both matches `ar-puuk/spatial-sql-explorer`'s own real "Graduated" mode, which offers both classified and continuous variants). When `steps` is omitted, the scale is fully continuous — the existing `tableLogic.ts`/`sankeyColor.ts` default behavior, unchanged.

## §11. `loadZoneGeometry()`'s `boundaries_id` gap — a mismatch across panels sharing one `boundaries` file MUST fail loudly, not silently pick a winner

A real gap in the original contract draft, caught before implementation began (same category of gap FR-003a caught for cache eviction — this one sits one level deeper in the same mechanism, not a new mechanism): `loadZoneGeometry(boundaries: string)`'s signature had no way to receive `boundaries_id` at all, even though the geometry query it builds (§3) needs it to select the right zone-id column (`SELECT "${boundariesId}" AS zone_id, ...`). Because the cache is deliberately keyed on `boundaries` alone and shared across every panel instance referencing that file (FR-003, §4), two panels naming the same `boundaries` file but different `boundaries_id` values is a real, reachable case this contract must define behavior for — not an edge case that happens to never occur.

**Is a same-file, different-`boundaries_id` case ever legitimate?** Checked against what a `boundaries` file actually represents: one GeoParquet file is one fixed zone system (TAZ boundaries, or a coarser district boundaries — `project-docs/GRAMMAR.md`'s own examples), with one natural id column. A deployment wanting a second granularity (e.g. district-level) publishes a *second* `boundaries` file (`district.geoparquet`), not a second id column bolted onto the same file referenced inconsistently. Two panels naming the same `boundaries` file with different `boundaries_id` values is therefore, in realistic practice, almost always a config-authoring mistake (a typo, or copy-pasting one panel's config and forgetting to update `boundaries_id` for a file that actually uses a different column name) — not a legitimate use case the cache needs to support transparently.

**Decision: `loadZoneGeometry(boundaries: string, boundariesId: string): Promise<ZoneGeometry>` — the cache entry records the `boundariesId` that created it, and a later call naming the same `boundaries` with a DIFFERENT `boundariesId` is rejected immediately with a descriptive error, never silently served from the first caller's cache entry.** Concretely:
- A call whose `boundaries` has no existing cache entry creates one, recording both `boundariesId` and the resulting load.
- A call whose `boundaries` already has an entry with the SAME `boundariesId` returns that exact same pending/resolved promise — the cache-hit path FR-003/§4 exists for, working exactly as intended.
- A call whose `boundaries` already has an entry with a DIFFERENT `boundariesId` returns `Promise.reject(new Error(...))` **synchronously, before any network activity** — the mismatch is knowable from the two strings alone, so there's no reason to wait on anything. Critically, this does **not** disturb the existing cache entry: every other, correctly-configured panel sharing that `boundaries` file keeps working unaffected by one misconfigured panel elsewhere on the same or a different tab. `ZoneMapPanel.tsx`'s existing geometry-fetch effect (contracts/zonemap-panel.md) already treats a rejected `loadZoneGeometry()` promise as `geometryStatus: 'error'`, routing to the shared `PanelErrorState` — the same "unresolvable configuration" path FR-010 already defines for a bad `boundaries`/`boundaries_id`/`metric_id`/`column`, so this mismatch needs no new error-handling branch, only the detection itself.

**Alternatives considered and rejected**:
- **First-caller-wins, silently** (the original, implicit behavior before this gap was caught) — rejected. The second, misconfigured panel would render a choropleth that *looks* fine (zones, colors, no error) but is silently joined against the wrong id column semantics from the first caller's load, or against zone ids that don't actually match its own intended column at all — exactly the kind of wrong-but-not-crashing outcome this project's established convention (an unresolvable `metric`/column already surfaces the shared error state loudly, never silently) exists to avoid. It would also make the bug nearly impossible to spot from the rendered output alone.
- **Compound-keying the cache on `(boundaries, boundaries_id)` instead of erroring** — rejected. This would technically "work" (each distinct pair gets its own cache entry, no error path needed at all), but it silently defeats the entire reason the cache is keyed on `boundaries` alone in the first place (§4, FR-003: multiple panels referencing the *same* file should share *one* geometry load) for exactly the case — a typo'd `boundaries_id` — that's most likely to produce two near-identical cache entries for what was actually meant to be one shared file, doubling the load with no signal to the author that anything is wrong.
