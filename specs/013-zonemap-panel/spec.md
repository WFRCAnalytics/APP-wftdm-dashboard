# Feature Specification: ZoneMapPanel

**Feature Branch**: `013-zonemap-panel`

**Created**: 2026-09-02

**Status**: Draft

**Input**: User description: "Add the eighth and final originally-listed panel type — zonemap — to the registry, following the same pattern as every prior data-bound panel type and inheriting 004's expand-to-dialog mechanism automatically (no per-type wiring). First GeoParquet/DuckDB-spatial feature in this codebase. Resolve whether a choropleth genuinely needs deck.gl or can be pure MapLibre before designing anything. MUST consume the existing panels/basemap/ module (011) unmodified. Research DuckDB-WASM's real spatial extension API and whether it has the same external-CDN-fetch behavior already documented for the parquet extension. Uses 002-design-tokens' tokens for the choropleth's own color scale, following established project color-convention precedent rather than inventing a new one. Needs real GeoParquet zone-boundary fixture data — this project's fixtures have so far only ever been tabular. Does not include: graphic-walker, or the map-controls feature (zoom/compass/3D-2D toggle)."

## Grammar & documentation findings (pre-spec verification)

Verified directly against `docs/GRAMMAR.md`, `docs/SPEC.md`, `docs/ARCHITECTURE.md`, `.specify/memory/constitution.md`, and the real `panels/basemap/` and `panels/tableLogic.ts`/`panels/sankeyColor.ts` source already in this repo before writing this spec — the same discipline every panel-type feature since `005-table-panel` has required. Two findings below correct assumptions embedded in the request that triggered this draft; both are stated plainly rather than silently designed around, matching this project's own established precedent (`010-flowmap-panel`'s `boundaries`/`boundaries_id` correction, the 012 constitution proposal's `APP-Commute-Explorer`-already-present correction).

1. **`type: zonemap` is real and already documented in two places**, not hypothetical: `docs/GRAMMAR.md`'s own worked example (`boundaries`/`boundaries_id`/`metric_id`/`column`/`label`/`color_scale`/`color_ramp`/`steps`/`domain`/`comparison`/`center`/`zoom`, plus a separate `diff`-mode example), and `docs/SPEC.md`'s Panel types table entry (`zonemap | MapLibre | GeoParquet join; setData() on update`) and its own "ZoneMapPanel wiring" code snippet.
2. **Config keys, confirmed against `docs/GRAMMAR.md`**: every panel's common keys (`type`/`title`/`metric`/`filter`/`height`/`width`/`scenario`/`scenarios`) apply here too, plus type-specific `boundaries` (a GeoParquet file), `boundaries_id` (the geometry's own zone-id column), `metric_id` (the matching zone-id column in the queried metric result), `column` (which metric column drives the fill), `label`, `color_scale` (`sequential | diverging`), `color_ramp` (a named ramp, e.g. `YlOrRd`/`RdBu`), `steps`, `domain` (optional — auto-computed when omitted), `comparison` (`side_by_side` default, or a `diff` object: `{ type: diff, a, b, expr }`), `center`, `zoom`.
3. **Placeholder usage, directly answering the request's own question**: `filter:` uses the same `$filters.x`/inline/`$ref` convention every other panel type already uses (a common key, not type-specific). `column`/`metric_id`/`boundaries_id` are **author-configurable field names naming literal columns already present in the queried result / geometry**, the same field-mapping convention `TableColumnConfig.field`, `SankeyPanelConfig`'s `source`/`target`/`value`, and `010-flowmap-panel`'s own `origin`/`origin_lat`/... keys already use — **not** `$metric.`-prefixed placeholders, which are specific to `plotly`/`observable-plot`'s trace-axis bindings and have no equivalent here.
4. **Rendering model — the constitution's own reference description and `docs/SPEC.md`'s own pre-existing documentation already point to pure MapLibre, not deck.gl.** `docs/SPEC.md`'s Panel types table lists zonemap's library as plain `MapLibre` (contrast flowmap's own row: `flowmap.gl + MapLibre | MapboxOverlay + FlowmapLayer`), and its "ZoneMapPanel wiring" snippet uses a bare `map.getSource('zones').setData(geojson)` call — no `MapboxOverlay`, no deck.gl layer, no second WebGL context anywhere in either place. `.specify/memory/constitution.md`'s own Principle VIII entry for `ar-puuk/spatial-sql-explorer` says "**MapLibre** choropleth, basemap switching" — not "deck.gl choropleth." This was the project's own documented direction before this feature existed, not a decision invented here. Per the request's own explicit standard, planning must still confirm no real, specific capability gap (e.g. a picking/interaction need MapLibre's native `fill` paint layer can't cover) forces deck.gl before treating this as final — but the default target this spec assumes, and that `docs/SPEC.md` already commits to in writing, is **one MapLibre GeoJSON source + a data-driven `fill-color` paint expression, one WebGL context per panel, zero deck.gl/`MapboxOverlay`/`012`'s interleaved-mode machinery** unless that confirmation finds otherwise.
5. **Reference implementations for this feature are already mandated in Principle VIII — no constitution amendment is needed.** `ar-puuk/spatial-sql-explorer` ("DuckDB spatial extension lazy-load, MapLibre choropleth, basemap switching") and `ar-puuk/parquet-viewer` ("GeoParquet metadata detection, `registerFileBuffer`, spatial extension fallback, buffer-pool collision fix") have both been in the mandate-tier table since the constitution's v1.0.0 ratification — confirmed directly against the current file text, and cross-checked against the already-merged `012-webgl-context-management` constitution amendment, which verified the same table for an unrelated reason. Principle VIII's MUST-copy requirement already applies to this feature without any new entry.
6. **`panels/basemap/` (011) was already built generically for this feature, not flowmap-specific** — its own `types.ts` header comment says "shared basemap registry/resolution, consumed by `FlowMapPanel.tsx` now, `ZoneMapPanel.tsx` once built (designed generically for exactly that, not flowmap-specific)," and `CLAUDE.md`'s own file-tree note repeats the same intent. `resolveEffectiveBasemap()`, `loadBasemapStyle.ts`, the built-in preset registry, and the panel > tab > app-default precedence are all reused unmodified — confirmed by direct inspection, not merely assumed generic.
7. **Color-convention correction**: the request pointed to `008-sankey-panel`'s established pattern, but direct inspection shows `008`'s `color_scheme` (`sankeyColor.ts`) is a **categorical** named-palette convention (Tableau10/Observable10/Category10/Set3 — discrete colors for discrete nodes/links), structurally unrelated to a **continuous** `sequential`/`diverging` scale. The actual existing precedent that matches zonemap's own `color_scale: sequential | diverging` + `domain` grammar is `005-table-panel`'s `tableLogic.ts` `cellColor()`: token-derived (`--brand-wfrc-blue`/`--destructive`/`--muted`), a `color-mix()` blend capped at `MAX_COLOR_STRENGTH = 40` for legibility, diverging scales anchored at a literal-zero midpoint (not the domain's geometric center), and out-of-domain values clamped to the nearest extreme's color. This is the convention to extend, not `008`'s. Zonemap's `color_ramp` (named-ramp) key has no existing equivalent in either precedent — closer in spirit to `sankeyColor.ts`'s recognized-name-else-token-fallback shape than to `tableLogic.ts`'s two hardcoded tokens — and is resolved during planning (Assumptions).
8. **`comparison: diff` is a genuinely new cross-scenario computation shape**, with no existing precedent in this codebase. Every prior panel type's multi-scenario support is either an overlaid `UNION ALL` (omit `scenario:`) or side-by-side single-scenario panel instances (`scenario:` key on each) — no prior panel type computes a per-row expression referencing two *named* scenarios' own column values (`a`, `b`, and a free-form `expr` like `"b.vmt_per_capita - a.vmt_per_capita"`) inside one panel. Resolved during planning, not designed here — see Assumptions. `comparison: side_by_side` (the grammar's own default) is read as the *non*-diff case: the panel renders its single selected/active scenario's values normally, the same as any other panel type using the existing side-by-side-panels convention (separate panel instances, each with its own `scenario:` key) — not a new UI concept.
9. **No real GeoParquet fixture exists in this project yet.** Every fixture built for `001` through `012` has been tabular Parquet only (`tests/fixtures/generate.py`). A real, small, public Utah/WFRC-area zone-boundary dataset, or a synthetic small polygon set, is needed — which one is decided during planning (Assumptions), not assumed here.
10. **DuckDB-WASM's spatial extension may share the parquet extension's own confirmed CDN-fetch behavior — unconfirmed, must be checked before shipping.** `docs/ARCHITECTURE.md`'s existing caveat (found during `010`) documents that DuckDB-WASM's `parquet` extension lazy-fetches its `.wasm` binary from `extensions.duckdb.org` on first query against any Parquet view, in every deployment mode including the "no internet required" `wftdm-dashboard here` — confirmed via a live `page.on('request')` capture, not assumed. Whether the `spatial` extension (needed for `ST_Read`/geometry parsing here) does the same is not yet confirmed either way. Planning MUST verify this with the same rigor (a live network capture, not documentation-reading) and, if confirmed, extend `docs/ARCHITECTURE.md`'s existing caveat rather than leave a second, silently undocumented network dependency.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Author renders a zone-level metric as a choropleth (Priority: P1)

A dashboard author adds a `type: zonemap` panel to a `dashboard-*.yaml` file, pointing it at a GeoParquet zone-boundary file and a metric column to color by. When the tab loads, the panel shows a MapLibre base map with every zone shaded according to its value on a color scale — letting an analyst see at a glance which parts of the region have the highest/lowest VMT per capita, mode share, or any other zone-level metric, the same way `vmt_by_home_taz` already exists in `summarize.yaml` specifically to feed this panel type.

**Why this priority**: This is the core, and only, reason this panel type exists (`docs/SPEC.md`: zone-level choropleth) — without it there is nothing to test or ship, and it is the last of the eight originally-listed panel types still unbuilt.

**Independent Test**: Can be fully tested by loading a dashboard tab with one `type: zonemap` panel against fixture geometry and metric data with known zone ids and values, and confirming each rendered zone's fill color matches what a direct join + color-scale computation of that same data would produce.

**Acceptance Scenarios**:

1. **Given** a `type: zonemap` panel configured with `boundaries`/`boundaries_id`/`metric_id`/`column`, **When** its bound metric returns zone-level rows, **Then** the panel renders a MapLibre base map with every zone in the boundary geometry shaded per its joined metric value, using the configured `color_scale`/`color_ramp`/`domain`.
2. **Given** the same panel, **When** it first renders, **Then** the map is centered/zoomed per the panel's `center`/`zoom` config (or a documented default when omitted, matching `010-flowmap-panel`'s own precedent for the same two keys).
3. **Given** the same panel with no `domain` configured, **When** the metric result loads, **Then** the color scale's domain is auto-computed from the actual min/max of the mapped `column` across the returned rows.
4. **Given** a rendered zone, **When** an analyst hovers or clicks it, **Then** its underlying zone id and metric value are shown (exact mechanics resolved during planning — see Assumptions).

### User Story 2 - Zonemap panel responds to global filters, resizes correctly, and inherits the app's basemap system (Priority: P2)

A dashboard author binds the zonemap panel's `filter:` key to a global sidebar filter, and the panel sits on a tab with a `default_basemap:` set. When a viewer changes the filter, the choropleth re-colors in place — the map instance itself is never recreated. The panel picks up the tab's basemap the same way a flowmap panel already does, with no zonemap-specific basemap code, and renders correctly sized both inline and inside 004's expand dialog, and on a plain browser window resize.

**Why this priority**: Filter-reactivity, resize correctness, and basemap inheritance are all baseline behavior every other panel type (and `010-flowmap-panel` specifically, the other map-rendering panel type) already guarantees; a zonemap panel that regressed any of them would break an established, tested contract rather than merely lack a feature.

**Independent Test**: Can be fully tested by changing a bound global filter's value while a zonemap panel is visible and confirming its choropleth re-colors via `setData()` without the underlying `maplibregl.Map` instance being destroyed/recreated; by setting a tab's `default_basemap:` with no panel-level `basemap:` override and confirming the zonemap panel renders it identically to how a flowmap panel on the same tab would; and by expanding/collapsing the panel via 004's dialog and resizing the browser window, confirming the map canvas fills its container correctly in both cases.

**Acceptance Scenarios**:

1. **Given** a zonemap panel's `filter:` bound to a global filter, **When** the filter's value changes, **Then** the panel re-queries and its zone fills update to reflect only matching rows, via the existing GeoJSON source's `setData()` — never a new `maplibregl.Map` instance or a full source re-add.
2. **Given** a zonemap panel with no `basemap:` of its own on a tab with `default_basemap:` set, **When** the panel loads, **Then** it renders the tab's default basemap using the unmodified `panels/basemap/` resolution the same way a flowmap panel on the same tab would (panel > tab > app-default precedence, per `011-basemap-style-system`).
3. **Given** a zonemap panel whose resolved basemap is unreachable or misconfigured, **When** the panel loads, **Then** the choropleth itself still renders (falls back to the blank basemap background, per `011`/`012`'s existing guarantee) — a basemap failure never blocks the panel's own data-driven content.
4. **Given** a rendered zonemap panel, **When** the viewer expands it into the 004 dialog and later collapses it, **Then** the map canvas resizes to fill its new container correctly in both directions, with no distortion, no re-fetch, and no map-instance recreation.
5. **Given** a rendered zonemap panel, **When** the browser window itself is resized, **Then** the map canvas resizes to match, without requiring a manual page refresh.

### User Story 3 - Author configures a color scale and a two-scenario diff comparison (Priority: P3)

A calibration analyst configures a zonemap panel's `color_scale`/`color_ramp`/`domain` to control how values map to color, and — for a panel comparing a base-year run against a proposed scenario — sets `comparison: diff` naming the two scenarios and an expression (e.g. modeled minus observed, or scenario B minus scenario A) so the map shows where the two runs diverge at the zone level, using a diverging scale anchored at zero.

**Why this priority**: This is the panel type's specific calibration/validation value beyond "render one metric" — it's what makes a zonemap panel useful for the same base-vs-horizon-year comparison work every other panel type in this app already supports in its own way, but it is not required for the panel type to exist at all (User Story 1 already delivers a usable panel without it).

**Independent Test**: Can be fully tested by configuring one zonemap panel with `color_scale: sequential` and a fixed `domain`, confirming its fill colors match a direct scale computation of the fixture data; and a second zonemap panel with `comparison: diff` naming two fixture scenarios and a simple `expr`, confirming its computed per-zone diff values and diverging fill colors match a direct computation of `b - a` for those same fixture rows.

**Acceptance Scenarios**:

1. **Given** a zonemap panel with `color_scale: sequential` and a fixed `domain`, **When** the metric loads, **Then** each zone's fill color matches the token-derived, capped color-mix() computation of its value against that domain (`005-table-panel`'s established convention, extended here — see Grammar findings #7).
2. **Given** a zonemap panel with `color_scale: diverging`, **When** a zone's value is exactly at the domain's non-zero geometric center, **Then** its fill color is NOT the scale's "neutral" midpoint color — the midpoint is anchored at literal zero, not the domain's center, matching `005`'s own established diverging-scale behavior.
3. **Given** a zonemap panel with `comparison: diff` naming two loaded scenarios and an `expr`, **When** both scenarios' data is available, **Then** the panel computes and renders the per-zone diff value using a diverging scale.
4. **Given** a `comparison: diff` panel where one of the two named scenarios is not currently loaded/active, **When** the panel renders, **Then** it shows the same shared error or empty state every other panel type shows for an unresolvable configuration — not a partial or silently wrong computation.

### User Story 4 - Zonemap panel behaves consistently with the rest of the panel registry (Priority: P4)

A dashboard tab contains a zonemap panel alongside every other panel type. It uses the same loading skeleton convention, the same shared error/empty states for a rejected query or zero-row result, and inherits 004's expand-to-dialog mechanism with zero zonemap-specific wiring — exactly as already guaranteed for every other panel type, completing the originally-listed eight-panel-type set.

**Why this priority**: Inherited "for free" from the registry pattern by construction, but — like `010-flowmap-panel` before it — this panel's own map-instance lifecycle (a live `maplibregl.Map`, a GeoJSON source, a module-level geometry cache) must not break that guarantee, so it warrants its own independently-testable story rather than being assumed as a side effect.

**Independent Test**: Can be fully tested by loading a tab mixing a zonemap panel with all seven other panel types and confirming all render without error, plus confirming a deliberately broken config (unresolvable metric, missing/misnamed `boundaries`/`boundaries_id`/`metric_id`/`column`) renders the shared error state instead of crashing.

**Acceptance Scenarios**:

1. **Given** a rendered zonemap panel, **When** the viewer clicks its expand trigger, **Then** the dialog shows the same choropleth (same underlying query result and geometry, not re-fetched) resized to the larger container, with the map instance itself preserved.
2. **Given** a zonemap panel configured with a `metric` no scenario publishes, or a `boundaries` file that fails to load, **When** the panel renders, **Then** it shows the same shared error state used by an unresolvable config on any other panel type — not an unhandled exception, and no partially-initialized MapLibre instance left behind.
3. **Given** a dashboard tab mixing a zonemap panel with every other already-built panel type (`valuebox`, `plotly`, `table`, `markdown`, `observable-plot`, `sankey`, `flowmap`), **When** the tab loads, **Then** all eight panels render without error in a single load.

### Edge Cases

- **What happens when a metric row's `metric_id` value has no matching zone in the boundary geometry?** Excluded before rendering — a value with no geometry to attach to can't be shown (same non-renderable-row exclusion discipline `010-flowmap-panel`'s own missing-coordinate handling already established).
- **What happens when a zone in the boundary geometry has no matching metric row?** Rendered with a distinct "no data" visual treatment (not the color scale's zero/minimum color, and not silently omitted from the map) — the zone's shape stays visible so the map's overall geography stays legible.
- **What happens when a value falls outside the configured (or auto-computed) `domain`?** Clamps to the nearest extreme's color, matching `005-table-panel`'s already-established `clamp01` behavior — not a new convention.
- **What happens when the bound metric returns zero rows?** Shown via the shared `PanelEmptyState`, same as every other data-bound panel type — the map is not initialized in this state.
- **What happens when `boundaries`, `boundaries_id`, `metric_id`, or `column` names a file/column that doesn't exist or fails to load?** Shown via the shared error state, same as an unresolvable `metric` on any other panel type.
- **What happens when a `comparison: diff` panel's `a`/`b` scenario names aren't both currently loaded/active?** Shown via the shared error/empty state (User Story 3, Scenario 4) — never a partial or silently-wrong diff.
- **What happens to the panel's resolved basemap if it's unreachable or misconfigured?** The choropleth still renders (User Story 2, Scenario 3) — extends `011`/`012`'s existing "a missing/unreachable basemap never prevents a panel's own data-driven content from rendering" guarantee to this panel type.
- **What happens when multiple zonemap panels on one tab reference the same `boundaries` GeoParquet file?** The geometry is parsed once and reused, not independently re-fetched/re-parsed per panel instance — `docs/SPEC.md`'s own "ZoneMapPanel wiring" snippet already documents a module-level cache for exactly this reason.
- **What happens to a cached zone geometry entry once every panel referencing its `boundaries` file has unmounted?** The cache's lifetime is deliberately decoupled from any individual panel's lifetime (FR-003 loads it once at module scope; FR-013's teardown is per-panel, on the `maplibregl.Map` instance only — it has no reference to, and does not touch, the geometry cache). Nothing in this spec evicts a cache entry when its last referencing panel unmounts. This is flagged here explicitly, not left implicit: for a long-running session touching many tabs/scenarios that each point at different, possibly large, `boundaries` files, the cache can grow unboundedly for the life of the page. See FR-003a and Assumptions — planning MUST state a decision (accepted tradeoff, with a stated reason, vs. a basic cap/LRU) rather than let this sit undocumented, the same way the `extensions.duckdb.org` network dependency sat undocumented until `010-flowmap-panel` happened to surface it (Grammar findings #10).
- **What happens to a live `maplibregl.Map` instance when `panelExpandHost.tsx`'s 004 mechanism relocates the panel during expand/collapse?** `010-flowmap-panel`'s own empirical finding (a real Playwright-verified same-document `appendChild` reparent survives cleanly) already answers this for the underlying MapLibre canvas itself — this feature does not need to re-derive that question from scratch, only confirm the additional GeoJSON-source/`setData()` lifecycle survives the same relocation (lighter confirmation, not a full re-investigation).
- **What happens on unmount (tab switch away, or the scenario driving this panel deactivated)?** The `maplibregl.Map` instance is torn down via `map.remove()` in a dedicated unmount-only effect, matching every other panel type's own teardown convention.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide a `zonemap` panel type that resolves `type: zonemap` `dashboard-*.yaml` entries to a choropleth component via `panels/registry.tsx`, inheriting the 004 expand-to-dialog mechanism automatically with no per-type wiring.
- **FR-002**: Panel MUST support the common data-bound panel keys already shared by every other panel type (`title`, `metric`, `filter`, `height`, `width`, `scenario`, `scenarios`) plus the documented `zonemap`-specific keys: `boundaries`, `boundaries_id`, `metric_id`, `column`, `label`, `color_scale`, `color_ramp`, `steps`, `domain`, `comparison`, `center`, `zoom`.
- **FR-003**: Panel MUST load the `boundaries` GeoParquet file's geometry once (not per data update, and not independently per panel instance when multiple panels share the same `boundaries` file — see Edge Cases) and join it to metric rows by `boundaries_id`/`metric_id` on each data update via `setData()` on the existing GeoJSON source — never a full source re-add or map recreation.
- **FR-003a**: The zone geometry cache's lifetime policy MUST be an explicit, stated decision — not an unstated side effect of FR-003's caching. Planning's `research.md` MUST record, by name, either (a) an accepted, deliberate tradeoff to let cache entries persist for the page session's full lifetime regardless of referencing-panel unmounts, with the reasoning that justifies it (e.g., `boundaries` files are expected to be small and few across a typical deployment's dashboard configs), or (b) a basic cap/eviction mechanism (e.g., LRU) and its trigger condition. A real eviction implementation is not required now; an explicit, reasoned decision is (Edge Cases).
- **FR-004**: Panel MUST render the choropleth as a MapLibre GeoJSON source with a data-driven `fill-color` paint expression — no deck.gl/`MapboxOverlay` and no second WebGL context per panel, unless planning-phase research (Grammar findings #4) confirms a real, specific capability gap requires it. If deck.gl is confirmed necessary, it MUST be built interleaved (`interleaved: true`) from day one, reusing `012-webgl-context-management`'s already-proven `MapboxOverlay`/`setStyle()`-survival/context-loss-detection pattern directly, not shipped non-interleaved first.
- **FR-005**: Panel MUST consume the existing `panels/basemap/` module (`resolveEffectiveBasemap`, `loadBasemapStyle`, the built-in preset registry, panel > tab > app-default precedence) unmodified — not a separate or duplicated basemap mechanism. An unreachable or misconfigured resolved basemap MUST NOT prevent the choropleth itself from rendering.
- **FR-006**: Panel's `color_scale: sequential | diverging` + `domain` MUST follow `005-table-panel`'s established token-derived, capped `color-mix()` convention (`tableLogic.ts`'s `cellColor()` — diverging midpoint anchored at literal zero, out-of-domain values clamped to the nearest extreme), not a newly invented color convention (Grammar findings #7). A recognized `color_ramp` name resolves to a concrete scale; an omitted or unrecognized one falls back to the token-derived default, mirroring `sankeyColor.ts`'s recognized-name-else-fallback shape.
- **FR-007**: When `domain` is omitted, the panel MUST auto-compute it from the actual min/max of the mapped `column` across the returned metric rows.
- **FR-008**: Panel MUST support `comparison: diff` (computing and rendering a two-named-scenario per-zone expression on a diverging scale) and `comparison: side_by_side` (the grammar's own default — rendering the single selected/active scenario's values normally, the same convention every other panel type's side-by-side scenario panels already use). `comparison: diff` MUST NOT use `eval()` or any dynamic code execution to compute `expr` — SQL fragments use string replacement only (constitution non-negotiable).
- **FR-009**: Panel MUST re-query and re-color via `setData()` (never recreate the map instance) when a bound `filter:` value changes.
- **FR-010**: Panel MUST use the same inline loading-skeleton convention, shared `PanelEmptyState` for a zero-row result, and shared `PanelErrorState` for a rejected query or unresolvable configuration (missing/misnamed `boundaries`/`boundaries_id`/`metric_id`/`column`, or an unresolvable `comparison: diff` scenario pair) that every other panel type already uses.
- **FR-011**: The rendered map MUST NOT visually distort, and MUST NOT require a manual refresh or re-fetch, when its container is resized — both via the 004 expand/collapse dialog transition and a plain browser window resize.
- **FR-012**: A metric row whose `metric_id` has no matching zone in the boundary geometry MUST be excluded before rendering; a zone with no matching metric row MUST render with a distinct "no data" treatment rather than being omitted or crashing the panel (Edge Cases).
- **FR-013**: On unmount, the panel MUST tear down its `maplibregl.Map` instance via `map.remove()` in a dedicated unmount-only effect, matching every other panel type's own teardown convention.
- **FR-014**: System MUST confirm, during planning, whether DuckDB-WASM's `spatial` extension shares the `parquet` extension's already-documented `extensions.duckdb.org` lazy-fetch behavior, and if so, extend `docs/ARCHITECTURE.md`'s existing "no internet required" caveat to cover it rather than leave a second, undocumented network dependency (Grammar findings #10).

### Key Entities

- **Zonemap panel config**: the common data-bound panel fields (`title`/`metric`/`filter`/`height`/`width`/`scenario`/`scenarios`) plus this panel type's own `boundaries`/`boundaries_id`/`metric_id`/`column`/`label`/`color_scale`/`color_ramp`/`steps`/`domain`/`comparison`/`center`/`zoom`/`basemap` keys.
- **Zone geometry cache**: the parsed GeoJSON `FeatureCollection` for a given `boundaries` GeoParquet file, loaded once (module-level, per-`boundaries`-file, per `docs/SPEC.md`'s own documented wiring and FR-003) and reused across data updates and panel instances sharing the same file. Its eviction policy (or the deliberate absence of one) is an explicit planning-phase decision, not an implementation detail left to be discovered later — see FR-003a.
- **Comparison result**: the `comparison: diff` mode's per-zone computed expression value between two named scenarios — a genuinely new derived entity with no existing precedent in this codebase (Grammar findings #8), structurally the zone-level analog of `010-flowmap-panel`'s own "Flow data" derived-entity precedent.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A zonemap panel's rendered per-zone fill colors match what a direct join + color-scale computation (sequential and diverging, including `comparison: diff`) of the same fixture geometry + metric data would produce.
- **SC-002**: Changing a bound global filter re-colors the zonemap panel's choropleth without a full page reload, without recreating the underlying map instance, and without any other panel re-rendering unnecessarily.
- **SC-003**: 100% of checks that expand a zonemap panel into the 004 dialog and collapse it again show a correctly proportioned map on both ends of the transition, with zero data re-fetch and zero map-instance recreation triggered solely by that transition.
- **SC-004**: An unreachable or misconfigured basemap never prevents a zonemap panel's own choropleth from rendering — 100% of checks against a deliberately unreachable basemap still show the data-driven fill.
