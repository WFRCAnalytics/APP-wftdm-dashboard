# Research: Protomaps PMTiles Basemap Support

## R-1: `@protomaps/basemaps` — real package, version, API surface

**Decision**: Add `@protomaps/basemaps` `^5.7.2` (real current npm version, confirmed via `npm view @protomaps/basemaps version` during this planning pass) as a direct dependency. Use its real exported `layers(sourceName, namedFlavor(flavorName), { lang: 'en' })` function to generate the MapLibre `layers` array at style-build time — never hand-author or persist a per-flavor style document.

**Rationale**: Confirmed directly (this session, carried into the spec) against Protomaps' own docs that a "flavor" is a plain color/property object, not a style file — `layers()` is the real, documented integration point. Confirmed this session via `npm view` that the package ships **zero runtime dependencies** (`dependencies: undefined`) and dual ESM/CJS builds with bundled `.d.ts` types — no peer-dependency coupling with `maplibre-gl` `^4.7.1` (the project's pinned version) to reconcile, unlike `@deck.gl/*`/`@flowmap.gl/layers`. Its output is a plain style-spec `layers` array — the same shape every other basemap composition path in `loadBasemapStyle.ts` already merges into a `StyleSpecification`, so no new merge mechanism is needed, only a new source of `layers`.

**Alternatives considered**: Hand-authoring 5 static style.json files (one per flavor) by running Protomaps' own generator once and committing the output. Rejected — the feature description is explicit that this is the wrong, unmaintainable path (a future Protomaps flavor-definition update would require manually regenerating and diffing 5 files); it also can't honor FR-004's "the same 5 flavors work against ANY deployer's own PMTiles URL," since a pre-baked style.json bakes in a specific `source` reference at generation time unless hand-edited afterward anyway.

## R-2: `pmtiles` client library — real package, version, protocol integration

**Decision**: Add `pmtiles` `^4.5.0` (real current npm version, confirmed via `npm view`) as a direct dependency. Register its `Protocol` class with MapLibre exactly once, via `maplibregl.addProtocol('pmtiles', protocol.tile)`, in a new small dedicated module (`panels/basemap/pmtilesProtocol.ts`) that performs the registration as a module-load-time side effect — ES modules are singleton-cached by the bundler/runtime, so importing this module from `loadBasemapStyle.ts` (the one shared resolution path every map-rendering panel and the Basemap-tab preview map already funnel through) guarantees registration happens exactly once, before any `pmtiles://`-sourced style is ever requested, with no change needed to `main.ts`'s boot sequence.

**Rationale**: Confirmed via `npm view` that `pmtiles`'s only real dependency is `fflate` `^0.8.2` (a small, pure decompression library) — no conflict with anything already in this project's dependency tree. `maplibregl.addProtocol` is MapLibre's own real, documented public API for exactly this "custom URL scheme" use case (already how this app's other three real `maplibregl` consumers — `FlowMapPanel.tsx`, `ZoneMapPanel.tsx`, `layout/settings/basemapTab.tsx`'s preview map — construct their `Map` instances; none of them registers any custom protocol today, confirmed via a direct grep for `addProtocol` returning zero existing matches, so this is genuinely new wiring, not a duplicate of something already there).

**Alternatives considered**: Registering the protocol in `main.ts`'s boot sequence (alongside `initDuckDB()`). Rejected in favor of the module-side-effect approach — `main.ts` is the whole app's boot path and has no other reason to know about basemap internals (every other basemap concern, including the one other one-time-setup-like concern, `resolveRasterProvider`'s cached catalog fetch, already lives inside `panels/basemap/`, not `main.ts`); a self-registering module keeps the entire PMTiles concern scoped to the basemap subsystem, consistent with this app's existing "generic engine, deployer-specific config" module boundary.

## R-3: Where the shared PMTiles source configuration lives

**Decision**: One new optional field on the existing `dashboard-config/index.json` discovery-file shape (`services/yamlLoader.ts`'s `DashboardIndexJson`/`DashboardBranding`) — e.g. `protomapsPmtilesUrl?: string` — resolved by the same `loadDashboardBranding()` function that already resolves `title`/`logoUrl`/`logoUrlDark`/`scenarioPalette`, with the same real/demo-root precedence and the same fail-soft "absent → undefined" parsing.

**Rationale**: This is the exact established, real precedent for "a deployer sets one config value, no source change, no new file type" in this app — `036-scenario-color-picker`'s `scenarioPalette` field was added to this identical shape for this identical reason (confirmed by reading `services/yamlLoader.ts` directly this session: `DashboardBranding` already documents itself as "richer shape for a discovery file that already existed... not a new config file type," Constitution Principle VII). A relative `public/`-bundled path and a full external URL are literally the same TypeScript `string` value passed to the same `pmtiles://` URL construction — no branching needed to support FR-004's "both forms behave identically."

**Alternatives considered**: A new, dedicated field on `dashboard-*.yaml` (tab-level `default_basemap`-style). Rejected — the PMTiles source is a single, deployment-wide value (like the app title/logo/scenario palette), not a per-tab or per-panel one; per-tab/per-panel *selection* of a Protomaps flavor already works today via the existing `basemap:`/`default_basemap:` panel/tab grammar (`BasemapPresetName` is already a plain `string`, so `"protomaps-light"` etc. need no grammar change at all to be selectable per-panel/per-tab) — only the shared *source* needed a new, deployment-wide home.

## R-4: Viewer session-only override — storage mechanism

**Decision**: A new, small in-memory state module (e.g. `state/protomapsSourceState.ts`), mirroring `state/basemapState.ts`'s existing shape exactly (a single module-level nullable value + `subscribe()`/`notify()`, no persistence). The Basemap tab's Protomaps section resolves its effective source as `viewerOverride ?? deployerDefault ?? undefined` (the "not configured" state per FR-010 when both are absent).

**Rationale**: Constitution Principle VI already forbids `localStorage`/`sessionStorage` for any state in this app — a plain in-memory module is both the constitutionally-required approach and the one that naturally satisfies FR-006's "never persists beyond the current session" (a page reload clears it for free, no explicit cleanup needed, matching how `state/basemapState.ts`'s own global basemap pick already resets on reload with "No persistence" called out explicitly in `CLAUDE.md`).

**Alternatives considered**: Extending `state/basemapState.ts` itself to also carry the PMTiles override. Rejected — that module's own header comment scopes it specifically to "the single, viewer-set global basemap choice" (a `BasemapPresetName | undefined`); the PMTiles override is a different kind of value (a source URL, not a preset name) serving a different question (what data the Protomaps *section* renders from, not which basemap is globally active), so a small sibling module keeps the same one-concern-per-module discipline `basemapState.ts` itself was split out from `appState.ts` to establish.

## R-5: Style assembly for a Protomaps flavor — source, sprite, glyphs, attribution

**Decision**: A new pure function, `panels/basemap/protomapsStyle.ts`'s `buildProtomapsStyle(flavorName, pmtilesUrl)`, returns a complete `StyleSpecification`:
- `sources`: one `protomaps`-type source, `{ type: 'vector', url: 'pmtiles://' + pmtilesUrl, attribution: PROTOMAPS_ATTRIBUTION }`.
- `layers`: the real, generated output of `@protomaps/basemaps`'s `layers('protomaps', namedFlavor(flavorName), { lang: 'en' })`.
- `sprite`: the confirmed-stable `https://protomaps.github.io/basemaps-assets/sprites/v4/{flavorName}` (Protomaps ships a per-flavor sprite sheet, not one shared sheet — matching each flavor's own distinct icon palette).
- `glyphs`: the confirmed-stable shared `https://protomaps.github.io/basemaps-assets/fonts/{fontstack}/{range}.pbf`.

This is a plain, DOM-free, Vitest-testable function — no MapLibre/browser API involved in building the object, matching every other pure style/encoding module in this codebase (`panels/basemap/loadBasemapStyle.ts`'s own `composeStyles()`, `panels/rechartsEncoding.ts`, etc.).

**Rationale**: Keeps flavor→style generation testable without a real browser/WebGL context (this project's established pattern for exactly this class of logic). The attribution string is the literal one confirmed this session: `'<a href="https://github.com/protomaps/basemaps">Protomaps</a> © <a href="https://openstreetmap.org">OpenStreetMap</a>'`, wired the same way every other basemap source's attribution already reaches MapLibre (a source-level `attribution` field, rendered by MapLibre's own built-in `AttributionControl` already present on every map instance in this app — confirmed via existing panels, no new attribution-control wiring needed).

**Alternatives considered**: Fetching sprite/glyph URLs at runtime from some discovery endpoint. Rejected — both are confirmed stable, static paths per the carried-forward research; hardcoding them is the same category of decision already made for OpenFreeMap's/CARTO's own hardcoded style URLs in `registry.ts` (an asset CDN path, not a region-specific data URL — the thing FR-005 actually forbids hardcoding is the *tile data* source, not a shared, generic asset host every flavor and every deployer equally depends on).

## R-6: Registry integration — how the 5 flavors join `BUILT_IN_PRESETS`

**Decision**: `BasemapPresetName` is already a plain `string` (confirmed by reading `panels/basemap/types.ts` — not a closed union), so the 5 new preset names (`protomaps-light`, `protomaps-dark`, `protomaps-white`, `protomaps-grayscale`, `protomaps-black`) need **zero type changes**. `loadBasemapStyle.ts`'s `resolvePresetName()` gains one new branch, checked alongside its existing built-in-preset/raster-provider branches: if the name matches one of the 5 Protomaps flavor names, resolve the current effective PMTiles source (R-4's precedence) and call R-5's `buildProtomapsStyle()`; if no source is configured, return the existing `freshBlankStyle()` fallback (same fail-soft convention as every other unreachable/unconfigured basemap case, satisfying FR-010/FR-011 with the mechanism that already exists rather than a new one).

**Rationale**: Reuses `resolvePresetName()`'s existing dispatch structure exactly, the same way the three real UGRC composition aliases (`021-basemap-catalog-redesign`) reused it rather than adding a parallel resolution path (Constitution/`CLAUDE.md`'s own "these are aliases, not a special case" precedent for exactly this kind of registry extension).

**Alternatives considered**: A `kind: 'protomaps'` tagged-union member on `BuiltInPreset` (mirroring the existing `UrlPreset`/`CompositionPreset` union). Considered viable but not chosen for the initial design — the 5 flavor names don't need a *static* registry entry at all (unlike a UGRC composition, which has a fixed URL list baked in), since their real resolution depends on a *runtime* value (the configured PMTiles source) that doesn't exist at module-load time. Handling them as a small, explicit name-check branch in `resolvePresetName()` (next to the existing raster-provider-name fallback branch, which already handles "not a literal built-in preset key") avoids forcing a runtime-dependent case into a registry object whose whole design assumption (`BUILT_IN_PRESETS: Record<name, ...>`) is that every value is static and known at load time.

## R-7: Test fixture — a small, real PMTiles file for integration tests

**Decision**: Implementation MUST source (not fabricate) a small, git-trackable PMTiles archive for Playwright coverage — generated via Protomaps' own real `pmtiles`/`planetiler` tooling against a tiny, deliberately small area (a handful of KB to low-single-digit MB), the same "prepare a small, real, git-tracked test asset" precedent `031-all-panel-demo-content`'s own `public/demo-geometry/taz25.geoparquet` already established for a different data type. This file is a **test-only fixture**, never a production default — it must not be wired into `public/demo-dashboard-config/index.json`'s own `protomapsPmtilesUrl` (the demo deployment ships with Protomaps genuinely "not configured," exercising FR-010's own required state honestly, since WFRC has not yet prepared a real Wasatch Front extract).

**Rationale**: FR-005/the carried-forward research are explicit that Protomaps' own demo-bucket/daily-build/hosted-API URLs must never be hardcoded as a *default* — a test-only fixture, self-hosted by this repo, sidesteps that entirely (it's not Protomaps' bucket, and it's not this app's shipped default either). Confirmed this session only that the two npm packages themselves exist and resolve at the stated versions; the exact fixture-generation command is implementation-detail deferred to task execution, not a spec/plan-level decision — recorded here as a MUST so it isn't silently skipped or, worse, silently replaced with a hotlinked Protomaps URL under test-writing time pressure.

**Alternatives considered**: Mocking `fetch`/the `pmtiles://` protocol handler entirely in tests (no real PMTiles bytes at all). Rejected as the *sole* coverage — this app's own established pattern (`zonemapPanel.spec.ts`, `flowmapPanel.spec.ts`) is to prove real rendering against real (if small) data wherever feasible; a real fixture is also the only way to prove R-1/R-2's actual library integration (protocol registration, real archive parsing, real `layers()` output rendering) rather than just this app's own glue code around a mocked library.

## R-8: Build — bundle chunking

**Decision**: Add `pmtiles`/`@protomaps/basemaps` to the existing `maps` `manualChunks` bucket in `vite.config.ts` (the same chunk `maplibre-gl` already resolves into), rather than a new dedicated chunk.

**Rationale**: Both packages are small (zero and one lightweight dependency respectively, confirmed in R-1/R-2) and are meaningfully useless without `maplibre-gl` already having loaded (they only ever run inside a MapLibre style-resolution path) — the same "only relevant alongside an already-required chunk" reasoning that keeps this project's existing chunk list from growing a dedicated bucket for every small addition (e.g. `d3-sankey`/`d3-scale-chromatic` were never split out from the main bundle either).

**Alternatives considered**: A dedicated `protomaps` chunk. Rejected as unnecessary given the confirmed small, dependency-light package sizes — revisit only if a real, measured build-output size regression is found during implementation (matching this project's own "measure before optimizing" discipline elsewhere, e.g. `029-shadcn-chart-panel`'s bundle-size checks).
