# Feature Specification: FlowMapPanel

**Feature Branch**: `010-flowmap-panel`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "Add a seventh panel type — flowmap — to the registry, following the same pattern as every prior data-bound panel type and inheriting 004's expand-to-dialog mechanism automatically. Uses the corrected project-docs/GRAMMAR.md type: flowmap grammar (origin/origin_lat/origin_lon/destination/dest_lat/dest_lon/value field-mapping keys, no boundaries/boundaries_id). Uses flowmap.gl + deck.gl, rendered via MapboxOverlay (non-interleaved mode) over a MapLibre GL base map, per project-docs/ARCHITECTURE.md's decision and SPEC.md's 'FlowMapPanel wiring' code snippet (create the overlay once, setProps() on update, map.remove() on destroy). First time this codebase renders an actual map — maplibre-gl, @deck.gl/core, @deck.gl/layers, @deck.gl/mapbox, @flowmap.gl/layers are all new dependencies (constitution v2.3.0 pins). Two real reference implementations already fetched and compared this session (WFRCAnalytics/APP-Commute-Explorer's FlowLayer.jsx, WFRCAnalytics/APP-WFRC-Commute-Patterns' map.js) — reuse their proven wiring per constitution Principle VIII. Research whether MapLibre/deck.gl need the same container-resize handling PlotlyPanel/ObservablePlotPanel/SankeyPanel each had to solve. Uses 002-design-tokens' tokens for container/card chrome; map base style and flow colors follow the panel config's own grammar. Reuse the query/fetch chain, loading/empty/error states, extractGlobalFilterIds, and the pure-module-extraction pattern for genuinely novel logic. Does not include: ZoneMapPanel, graphic-walker, or any other undelivered panel type."

## Grammar findings (pre-spec verification)

Verified directly against `project-docs/GRAMMAR.md`, `project-docs/ARCHITECTURE.md`, `project-docs/SPEC.md`, and two real production reference repositories before writing this spec, per this project's established discipline (005 through 009 each required the same) — this feature additionally required a live correction to `project-docs/GRAMMAR.md` itself, made and confirmed with the user before this spec was written (see Assumptions):

1. **`type: flowmap` is a real, documented panel type**, `project-docs/SPEC.md`'s Panel types table (`flowmap | flowmap.gl + MapLibre | MapboxOverlay + FlowmapLayer; setProps() on update`) and `project-docs/GRAMMAR.md`'s own worked example confirm it, not hypothetical.
2. **`origin`/`origin_lat`/`origin_lon`/`destination`/`dest_lat`/`dest_lon`/`value` are author-configurable field-mapping keys naming literal columns already present in the queried result set — corrected during this session, not the grammar's original shape.** The grammar previously had `boundaries`/`boundaries_id` keys implying a live GeoParquet zone-boundary join in the browser to resolve TAZ IDs into centroid coordinates. Verified against two real, fetched (not assumed) production reference apps — `APP-Commute-Explorer`'s `FlowLayer.jsx` and `APP-WFRC-Commute-Patterns`' `map.js` — neither does this: both construct `FlowmapLayer`'s `locations` from lat/lon values already present as plain columns on the flow data itself (`f.home_lat`/`f.home_lon`/`f.work_lat`/`f.work_lon` and `loc.lat`/`loc.lon` respectively). `project-docs/GRAMMAR.md` was corrected to match this proven pattern before this spec was written — see that file's own inline correction note. This is the same author-names-the-field approach `TableColumnConfig.field`/`SankeyPanelConfig`'s `source`/`target`/`value` already use, applied here to six coordinate/id/magnitude fields instead of two/three.
3. **Zone-centroid resolution is entirely an offline, post-processor concern — not this feature's.** `project-docs/ARCHITECTURE.md`'s "all format conversion... happens offline — the browser only ever reads Parquet" principle already covers this; `project-docs/CALIBRATION-SUMMARIES.md` was updated to flag the expectation for `od_flows.parquet`/`workplace_od_flows.parquet` once the (still-unbuilt) Python post-processor exists. This feature touches no GeoParquet, no DuckDB spatial extension, and no `ST_Read`/`ST_Centroid` — confirming the feature description's own stated scope boundary now holds cleanly against the corrected grammar (it did not hold against the original, uncorrected grammar).
4. **Sankey inherits the same common keys every data-bound panel type gets** (`project-docs/GRAMMAR.md` line ~906: `type/title/metric/filter/height/width/scenario/scenarios`) — flowmap's own worked example uses `filter: $filters.purpose` (bare-string `$ref` form), consistent with every prior panel type.
5. **No documented color-customization key for flow lines or nodes.** Unlike sankey's `color_scheme`, flowmap's grammar has no equivalent — `clustering`/`clustering_auto`/`animation`/`max_flows`/`center`/`zoom` are its only type-specific keys beyond the field mappings. Resolved in Assumptions: flowmap.gl's own default coloring applies, matching the already-established, honestly-documented precedent (research equivalent to 008's own finding) that not every chart panel type in this codebase actually overrides its library's default palette.
6. **Version pins confirmed directly, not assumed**: `maplibre-gl ^4.7.1`, `@deck.gl/core`/`@deck.gl/layers`/`@deck.gl/mapbox ^9.0.0`, `@flowmap.gl/layers ^9.3.0` — constitution v2.3.0's Technology Stack Reference, itself cross-checked this session against both real reference repos' actual `package.json` files (`@deck.gl/layers` was a real, confirmed gap added to the constitution as part of that verification).
7. **This is the first panel type that renders a real map** — `MapboxOverlay` (non-interleaved) added as a MapLibre control, hosting a `FlowmapLayer`; imperative lifecycle (create once, `setProps()` on data update, `map.remove()` on unmount) per `project-docs/SPEC.md`'s own "FlowMapPanel wiring" snippet — a fundamentally different rendering model from every prior chart panel type (none of which own a persistent, non-React-managed instance across the panel's full lifetime the way this one must).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Author renders an O-D metric as a flow map (Priority: P1)

A dashboard author adds a `type: flowmap` panel to a `dashboard-*.yaml` file, mapping a metric's origin/destination id and coordinate columns plus a magnitude column. When the tab loads, the panel shows a MapLibre base map with animated-capable desire lines connecting origin and destination locations, each line's width/weight reflecting its flow magnitude — letting an analyst see at a glance where the heaviest O-D movement is concentrated across the region.

**Why this priority**: This is the core, and only, reason this panel type exists (`project-docs/SPEC.md`: "O-D flows") — without it there is nothing to test or ship.

**Independent Test**: Can be fully tested by loading a dashboard tab with one `type: flowmap` panel against fixture data with known origin/destination/coordinate/value rows, and confirming the rendered flow lines' endpoints and relative widths match what a direct aggregation of that data would produce.

**Acceptance Scenarios**:

1. **Given** a `type: flowmap` panel configured with `origin`/`origin_lat`/`origin_lon`/`destination`/`dest_lat`/`dest_lon`/`value` field mappings, **When** its bound metric returns O-D rows, **Then** the panel renders a MapLibre base map with one deduplicated location per unique origin/destination id (keyed by id, not re-added per row) and one flow line per distinct (origin, destination) pair, each line's rendered weight proportional to its `value`.
2. **Given** the same panel, **When** it first renders, **Then** the map is centered/zoomed per the panel's `center`/`zoom` config (or a documented default when omitted).
3. **Given** the same panel with `clustering: true`, **When** the map is zoomed out far enough that nearby flows would visually overlap, **Then** flowmap.gl's own zoom-adaptive clustering behavior applies (this panel type configures it; it does not reimplement it).

---

### User Story 2 - Flowmap panel responds to global filters and resizes correctly (Priority: P2)

A dashboard author binds the flowmap panel's `filter:` key to a global sidebar filter. When a viewer changes that filter's value, the panel re-queries and updates its flow lines in place — the map instance itself is never recreated, and hover/pan/zoom state a viewer had before the filter change is not needlessly disrupted where the underlying library allows preserving it. The map also renders correctly sized both inline and inside 004's expand dialog, and on a plain browser window resize.

**Why this priority**: Filter-reactivity and correct-sizing-on-resize are both expected baseline behavior for every data-bound panel in this app (mirrors every prior panel type's own User Story 2); a flowmap panel that ignored either would be a regression from the established pattern.

**Independent Test**: Can be fully tested by changing a bound global filter's value while a flowmap panel is visible and confirming its flow lines update to reflect only matching rows without the map instance being destroyed/recreated (verifiable via `map.remove()` not being called and a stable DOM node), and by expanding/collapsing the panel via 004's dialog and resizing the browser window, confirming the map canvas fills its container correctly in both cases.

**Acceptance Scenarios**:

1. **Given** a flowmap panel's `filter:` bound (inline map or `$ref`) to a global filter, **When** the filter's value changes, **Then** the panel re-queries and its flow lines update to reflect only matching rows, via `overlay.setProps()` — never a new `MapboxOverlay`/`maplibregl.Map` instance.
2. **Given** a filter value that matches zero rows, **When** the panel re-queries, **Then** it shows the same shared empty state every other panel type shows for a zero-row result (the map itself is not rendered in that state, matching every other chart panel type's own loading/empty/error branching).
3. **Given** a rendered flowmap panel, **When** the viewer expands it into the 004 dialog and later collapses it, **Then** the map canvas resizes to fill its new container correctly in both directions, with no distortion and no re-fetch.
4. **Given** a rendered flowmap panel, **When** the browser window itself is resized, **Then** the map canvas resizes to match, without requiring a manual page refresh.

---

### User Story 3 - Flowmap panel behaves consistently with the rest of the panel registry (Priority: P3)

A dashboard tab contains a flowmap panel alongside other panel types. It uses the same loading skeleton convention, the same shared error/empty states for a rejected query or zero-row result, and inherits 004's expand-to-dialog mechanism with zero flowmap-specific wiring — exactly as already guaranteed for every other panel type.

**Why this priority**: Inherited "for free" from the registry pattern by construction, but this panel's own real map-instance lifecycle (unlike any prior panel's simpler DOM-node lifecycle) must not break that guarantee — worth its own independently-testable story rather than assumed as a side effect of User Story 1.

**Independent Test**: Can be fully tested by loading a tab mixing a flowmap panel with valuebox/plotly/table/markdown/observable-plot/sankey panels and confirming all render without error, plus confirming a deliberately broken config (unresolvable metric, or a missing required field mapping) renders the shared error state instead of crashing.

**Acceptance Scenarios**:

1. **Given** a rendered flowmap panel, **When** the viewer clicks its expand trigger, **Then** the dialog shows the same map (same underlying query result, not re-fetched) resized to the larger container, with the map instance itself preserved (not destroyed and recreated).
2. **Given** a flowmap panel configured with a `metric` that no scenario publishes, **When** the panel renders, **Then** it shows the same shared error state used by an unresolvable metric on any other panel type — not an unhandled exception, and no partially-initialized MapLibre instance left behind.
3. **Given** a dashboard tab mixing a flowmap panel with every other already-built panel type, **When** the tab loads, **Then** all panels render without error in a single load.

### Edge Cases

- **What happens when multiple rows share the same (origin, destination) pair?** Their `value` is summed into a single flow line before rendering — the panel must neither silently drop the extra rows nor render duplicate overlapping lines for the same pair (same discipline `008-sankey-panel`'s own duplicate-pair handling already established for a structurally similar problem).
- **What happens when a row's mapped `value` is zero or negative?** Excluded before rendering — a flow line cannot have negative/zero visual weight. Whether this needs a visibility signal (a `console.warn`, matching `008-sankey-panel`'s own precedent for its structurally identical exclusion case) or is silent is resolved in Assumptions.
- **What happens when a row is missing one of its required coordinate fields (e.g., `origin_lat` present but `origin_lon` null)?** That row is excluded from the flow set (same non-positive-value-style exclusion, not a per-field partial-render), on the reasoning that a location that can't be plotted can't contribute a valid flow line either.
- **What happens when `origin`, `destination`, `value`, or any of the four coordinate fields names a column absent from the query result?** Shown via the shared error state, same as an unresolvable `metric` on any other panel type.
- **What happens when the same location id appears with different coordinates across rows (e.g., `origin_lat`/`origin_lon` drift slightly between rows for the same `origin` id)?** The first-seen coordinate pair for a given id wins (matching the real reference apps' own `Map`-keyed-by-id dedup behavior, confirmed directly against their fetched source) — not an averaged or last-write-wins value.
- **What happens to the map's rendered size when the browser window itself is resized, or the panel moves into/out of the 004 expand dialog?** Must not distort or require a manual refresh (User Story 2, Scenario 3-4) — resolved via research into MapLibre's own native resize behavior plus the real reference apps' own defensive `ResizeObserver` usage; see Assumptions.
- **What happens to a live `maplibregl.Map`/deck.gl `MapboxOverlay` instance when `panelExpandHost.tsx`'s 004 mechanism relocates the panel during expand/collapse?** This is a distinct question from the resize case above — it's not asking whether the map reacts correctly to a new size, but whether the map (and its WebGL context, canvas, internal event listeners) survives being physically moved in the DOM tree at all. `panelExpandHost.tsx` does **not** recreate the panel's own container element or hand MapLibre a new one — it `appendChild`-moves a persistent *ancestor* node (`portalHostRef.current`) between an inline anchor and a dialog anchor, carrying every descendant (including whatever container `new maplibregl.Map({container: ...})` was constructed against) along as one native DOM subtree move, entirely outside React's reconciliation. This is a materially different, gentler operation than "point an existing map at a different container" (an unsupported ask per a real Mapbox GL JS GitHub issue, `#6165`, requesting a `setContainer()`-style API that doesn't exist) — but MapLibre's own docs/source were checked and don't explicitly confirm *this* exact scenario (an ancestor of its container being reparented via `appendChild` within the same document) either way. General WebGL/browser platform behavior treats a same-document canvas reparent as safe (context loss is normally tied to explicit `loseContext()` calls, GPU/driver resets, memory pressure, or a cross-document move — not a same-document `appendChild`), so the expectation is that it survives cleanly — but per FR-009, this is **resolved by real, empirical verification during planning/implementation, not asserted from research alone** (see Assumptions) — the same standard `004-panel-expand-dialog`'s own research applied to its analogous container-swap question, which only surfaced a real problem (a genuine remount) through an actual measured Playwright regression, not from reading library docs.
- **What happens when the bound metric returns zero rows?** Shown via the shared `PanelEmptyState`, same as every other data-bound panel type — the map is not initialized in this state.
- **What happens on unmount (tab switch away, or the scenario driving this panel deactivated)?** The `MapboxOverlay` and underlying `maplibregl.Map` instance are torn down via `map.remove()` — matching `project-docs/SPEC.md`'s own documented "destroy" step and every other panel type's own unmount-only teardown effect convention.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide a `flowmap` panel type that resolves `type: flowmap` `dashboard-*.yaml` entries to a flow-map component via `panels/registry.tsx`, inheriting the 004 expand-to-dialog mechanism automatically with no per-type wiring.
- **FR-002**: Panel MUST let the dashboard author map seven query-result columns via the documented `origin`, `origin_lat`, `origin_lon`, `destination`, `dest_lat`, `dest_lon`, and `value` keys — author-configurable field names naming literal columns already present in the queried result set, not `$metric.`-prefixed placeholders and not a live spatial join against a separate boundaries file (Grammar findings #2).
- **FR-003**: Panel MUST derive a location list and flow list from the flat query rows: one location per unique value in the mapped `origin`/`destination` columns (deduplicated by id, first-seen coordinates win — see Edge Cases), and one flow per distinct (origin, destination) pair, with each flow's value equal to the sum of the mapped `value` column across all rows sharing that pair.
- **FR-004**: Panel MUST support the common data-bound panel keys already shared by every other panel type (`title`, `metric`, `filter`, `height`, `width`, `scenario`, `scenarios`), including both the inline-map and `$ref` forms of `filter:`.
- **FR-005**: Panel MUST support the documented `clustering`, `clustering_auto`, `animation`, `max_flows`, `center`, and `zoom` keys, passed through to flowmap.gl's `FlowmapLayer`/the underlying MapLibre map's initial view state, with reasonable defaults when omitted (resolved in Assumptions).
- **FR-006**: Panel MUST render its map via a `MapboxOverlay` (non-interleaved mode) added as a MapLibre control, hosting a `FlowmapLayer`, per `project-docs/SPEC.md`'s documented wiring — imperative lifecycle: the `maplibregl.Map` and `MapboxOverlay` instances MUST be created exactly once per panel mount, updated via `overlay.setProps()` on data/filter change, and torn down via `map.remove()` only on unmount. The map instance MUST NOT be recreated on a data or filter change.
- **FR-007**: Panel MUST use the same inline loading-skeleton convention, shared `PanelEmptyState` for a zero-row result, and shared `PanelErrorState` for a rejected query or unresolvable configuration (missing/misnamed field-mapping column) that every other panel type already uses.
- **FR-008**: The rendered map MUST NOT visually distort, and MUST NOT require a manual refresh, when its container is resized — both via the 004 expand/collapse dialog transition and a plain browser window resize.
- **FR-009**: The panel's query result and rendered map MUST NOT reset or re-fetch, and the underlying map instance MUST NOT be destroyed and recreated, solely because the panel moved into or out of the 004 expand dialog. **This MUST be verified empirically against a real relocation, not assumed from documentation or general web-platform behavior alone** (see Edge Cases) — the same rigor `004-panel-expand-dialog`'s own research applied to its container-swap question, which found a real regression (a genuine remount) only via an actual measured Playwright test, not from reading React's docs.
- **FR-010**: Rows missing a required coordinate field, or contributing a non-positive mapped `value` (see Edge Cases), MUST be excluded from the location/flow set before rendering, and MUST NOT crash the panel. Whether this exclusion requires a visibility signal (vs. being silent) is resolved in Assumptions.
- **FR-011**: On unmount, the panel MUST tear down its `MapboxOverlay`/`maplibregl.Map` instance via `map.remove()` — a dedicated unmount-only effect, matching every other panel type's own teardown convention.

### Key Entities

- **Flowmap panel config**: the common data-bound panel fields (`title`/`metric`/`filter`/`height`/`width`/`scenario`/`scenarios`) plus this panel type's own `origin`/`origin_lat`/`origin_lon`/`destination`/`dest_lat`/`dest_lon`/`value` field-mapping keys and optional `clustering`/`clustering_auto`/`animation`/`max_flows`/`center`/`zoom`.
- **Flow data**: the location-list/flow-list structure this feature's rows-to-flowmap transform derives from flat query rows — a location list (unique ids with resolved lat/lon) and a flow list (each an origin location, destination location, and summed magnitude) — the genuinely new data-transform entity this feature introduces, structurally similar to `008-sankey-panel`'s own `FlowGraph` (nodes/links) but distinct in shape (geographic locations, not namespaced categorical nodes).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A flowmap panel's rendered locations and flows match what a direct `GROUP BY origin, destination` / `SUM(value)` aggregation of the same fixture query result would produce.
- **SC-002**: Changing a bound global filter updates the flowmap panel's flow lines without a full page reload, without recreating the underlying map instance, and without any other panel re-rendering unnecessarily.
- **SC-003**: 100% of checks that expand a flowmap panel into the 004 dialog and collapse it again show a correctly proportioned map on both ends of the transition, with zero data re-fetch and zero map-instance recreation triggered solely by that transition.
- **SC-004**: A zero-row query result and a rejected/unresolvable configuration each produce the same defined empty/error state already used by sibling panel types, with zero unhandled exceptions surfaced to the user, and no partially-initialized map instance left in the DOM.
- **SC-005**: A dashboard tab combining all seven now-built panel types (`valuebox`, `plotly`, `table`, `markdown`, `observable-plot`, `sankey`, `flowmap`) renders all of them without error in a single load.

## Assumptions

- **Resize handling is a planning-phase research question with a real, evidence-based starting point, not assumed either way**: MapLibre GL JS 3.0+ (this project pins `^4.7.1`) added native `ResizeObserver`-based auto-resize to its `Map` constructor — but the real, fetched `APP-Commute-Explorer` reference implementation still adds its *own* explicit `ResizeObserver` calling `map.resize()`, despite using a version with the native behavior already available. Whether that's defensive redundancy or addresses a real gap specific to this app's own 004 expand-dialog DOM-relocation mechanism (the same category of edge case `007`/`008` each needed custom handling for, in their own render libraries) is confirmed during planning, following the real reference app's own pattern rather than relying solely on MapLibre's native behavior unless research finds that's genuinely sufficient.
- **Whether a live `maplibregl.Map`/`MapboxOverlay` instance survives 004's `appendChild`-based relocation intact (WebGL context, canvas, internal event listeners) is resolved by real, empirical verification during planning/implementation, not asserted from research alone (FR-009, Edge Cases).** Research this session found: (a) 004's mechanism never hands MapLibre a new container — it relocates a persistent *ancestor* node, carrying the unchanged container (and everything inside it) along as one native DOM subtree move; (b) this is materially different from "point an existing map at a different container," which a real Mapbox GL JS GitHub issue (`#6165`) confirms is unsupported — not what 004 does; (c) general WebGL/browser platform behavior treats a same-document canvas reparent as safe (context loss is normally tied to explicit `loseContext()`, GPU/driver resets, or a cross-document move, not a same-document `appendChild`); (d) no MapLibre-specific documentation or source was found either confirming or prohibiting this exact scenario. Planning MUST include a real Playwright test performing the actual 004 relocation against a live map and asserting it renders/responds correctly afterward (e.g., the canvas retains valid dimensions, no `webglcontextlost` event fires, the map remains interactive) — mirroring `004-panel-expand-dialog`'s own research, which only found its real container-swap regression through actual measurement, not documentation-reading.
- **No documented color-customization key exists for flow lines/locations** (Grammar findings #5) — flowmap.gl's own default coloring applies. This is not a gap relative to established precedent: `research.md` from `008-sankey-panel` already found neither `PlotlyPanel` nor `ObservablePlotPanel` actually overrides its library's default categorical palette either: sankey building its own token-derived fallback palette was the exception, not the rule, and that exception was itself grammar-driven (`color_scheme` is documented sankey grammar; no equivalent exists for flowmap).
- **Non-positive-value/missing-coordinate exclusion visibility** (FR-010) is resolved during planning with real reasoning in `research.md`, following `008-sankey-panel`'s own precedent for its structurally identical `console.warn`-on-exclusion decision — not assumed silent by default.
- **`clustering`/`clustering_auto`/`animation`/`max_flows`/`center`/`zoom` default values** (FR-005) when omitted from a panel's config are resolved during planning against flowmap.gl's/`FlowmapLayer`'s own documented defaults, not invented here.
- The rows-to-flowmap transform (locations/flows derivation) is implemented as a pure, DOM-free module, mirroring `sankeyGraph.ts`'s own precedent (`008-sankey-panel`) — Vitest-testable without a real DOM or a real MapLibre/deck.gl instance. The specific module boundary and shape are a planning-phase design decision, not fixed here.
- This feature completes the map-rendering half of the two still-outstanding panel types alongside `zonemap` — `zonemap` remains explicitly out of scope (needs GeoParquet/DuckDB-spatial support this feature deliberately does not touch, per the corrected grammar's own reasoning), as does `graphic-walker`.
- `project-docs/GRAMMAR.md`'s `type: flowmap` correction (removing `boundaries`/`boundaries_id`, adding the six coordinate/id field-mapping keys) was made and confirmed with the user before this spec was written — not a planning-phase decision, already resolved.
